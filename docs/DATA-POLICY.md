# Данные и границы безопасности MVP

Это техническое описание тестового режима, не юридическое заключение и не политика готового сервиса для реального найма.

## Что хранится

Имя и MAX ID, компания работодателя, вакансии, согласие, текст опыта, ответы, приглашение, статусы и аудит действий. Для каждого отклика хранится производный кэш: канонические названия найденных навыков и номера предложений в резюме, где они встречаются. SHA-256 резюме позволяет повторно использовать кэш для того же пользователя при подаче на другую вакансию; исходный текст сверяется перед повторным использованием. Кэш не копирует текст резюме и очищается вместе с ним при отзыве. Для старых записей кэш заполняется один раз при миграции. Для тестовых API-аккаунтов — email и хеш пароля. Кнопки содержат случайный идентификатор, привязанный на сервере к пользователю; контекстные действия дополнительно проверяют состояние диалога. Срок кнопки — 24 часа.

Внешние сервисы runtime: MAX для сообщений; Caddy/центр сертификации для HTTPS. Необязательный ИИ-анализ резюме включён только при явно заданном `HIRING_AI_ENABLED`, конфигурации работодателя с реквизитами/публичным уведомлением и отдельном согласии кандидата. Без любого из этих условий текст резюме модели не отправляется. Пример конфигурации показывает Cloud.ru Foundation Models и внутреннюю GigaChat-модель; пользовательские providers настраиваются отдельно. Автоматических баллов, ранжирования и отказов нет.

При согласии сохраняются точный текст и его хеш/версия, решение и время, версия и ссылка на уведомление, модель/исполнитель и хеш исходного резюме. Секрет API берётся только из переменной окружения, не хранится в JSON/БД/ответах API. Перед передачей удаляются очевидные email, телефоны, URL и размеченные строки с прямыми идентификаторами; точные совпадения с именем из MAX-профиля маскируются. Это не является полной анонимизацией. Отправляется только текст до 12 000 символов; один запрос без автоматических повторов/резервных внешних моделей, максимум 700 токенов ответа. В сводку попадают только точные цитаты, найденные в отправленном тексте; произвольный вывод модели и рекомендации о найме отбрасываются. Рекрутер проверяет цитаты по исходному резюме.

Кандидат может продолжить без ИИ или отозвать только согласие кнопкой «Отозвать согласие на ИИ»; результат удаляется, сам отклик остаётся. ИИ-сводка автоматически удаляется из рабочей базы через настраиваемые 1-365 дней после формирования; минимальное подтверждение решения и аудит остаются, а их собственный срок хранения необходимо установить в политике оператора. Отзыв всего отклика очищает AI-результат и resume-хеш, но оставляет минимальную запись согласия и аудита. Если сетевой запрос к модели уже начался, бот не может отменить уже состоявшуюся обработку у провайдера. При настройке внешнего provider работодатель/оператор обязан проверить место обработки, договор и правовое основание; резервного переключения на бесплатные внешние API нет. Локализация основной базы и резервных копий зависит от фактического места размещения сервера и должна быть подтверждена отдельно.

При импорте ссылки бот обращается только к публичному API Яндекс Диска и его разрешённым адресам скачивания. Не вводить реальные персональные данные до согласования ответственного оператора, опубликованного уведомления, условий хранения и доступа.

GitHub, Google Drive и Mail.ru больше не импортируются. Старые сохранённые GitHub-обзоры и HR-заметки остаются только для совместимости удаления: отзыв отклика очищает и эти прежние копии. Никаких новых сетевых задач по ним нет.

При явном подключении HR-системы работодатель может читать свои данные через [интеграционный API](HR-INTEGRATION.md). По умолчанию ключ не раскрывает имя, резюме и ответы; для детальной карточки требуется отдельное право `applications:pii`. Выдача такого права и доступ получателя требуют проверки оператором. Хранятся хеши ключей, сроки/права/отзыв, соответствия внешних ID и лента ID/типов/времени изменений без текстов кандидата. Автоматической отправки в произвольные внешние URL нет.

## Отзыв и хранение

Отзыв очищает resume/resume_sha256/normalized_skills/answers/questions/invitation и AI-результат в Application/AIReview. Связанные копии в Outbox очищаются, pending/failed отменяются. Минимальные сведения о согласии (время, версия, точный текст и его хеш) и метаданные аудита остаются для подтверждения выбора; это тоже персональные данные и требует установленного срока хранения. Для старых сообщений без связи с откликом и списков с именами очищаются неассоциированные сообщения обоих участников: это консервативное ограничение миграции и приватности, поэтому меню иногда нужно открыть заново. Сами вакансии и метаданные аудита остаются.

После успешной доставки новый sender сразу очищает payload в своей БД. При ошибке текст остаётся для повторов; `maintenance prune` удаляет старые sent/failed/cancelled записи старше 7 дней, истёкшие кнопки и события старше 7 дней. По умолчанию команда только показывает план, изменения требуют `--apply`. Она не удаляет действующие вакансии или аккаунты.

Под событиями в `maintenance prune` здесь понимаются записи дедупликации MAX, не интеграционная лента. Для ленты изменений автоматическая очистка пока не реализована. После отзыва API отдаёт только tombstone; HR-получатель обязан удалить ранее выгруженные тексты и производные копии самостоятельно. Бот не может физически очистить стороннюю ATS. Восстановление старой БД требует также полной пересинхронизации интеграций и сброса их курсоров.

Плановый регламент тестового стенда: оператор запускает очистку технических записей ежедневно, хранит резервные копии не более 7 дней и завершает хранение синтетической базы не позднее 30 дней после технической проверки. Это пока ручной регламент, расписание не настроено. До согласования реального пилота использовать только вымышленные сведения.

Уже доставленные сообщения в MAX, их пересылки и резервные копии отзывом не удаляются. После восстановления старой копии оператор должен повторно применить журнал отзывов до включения рассылки. Проверка DATA-API использует отдельный стенд; её cleanup закрывает вакансию и отзывает отклик, но не является полным физическим удалением всех метаданных. После проверки стенд утилизируется отдельно с подтверждением владельца.

## Границы и остаточные риски

- Проверяются принадлежность вакансии/отклика, webhook secret, подпись MAX initData и JWT. Кнопки одноразовые, чужие/устаревшие отклоняются.
- Вход работодателя в боте ограничен пятью попытками за 10 минут на MAX-пользователя. HTTP-auth ограничен в памяти процесса, не распределённо.
- Входные тела ограничены, TLS-проверка не отключается. Дополнительный корневой сертификат используется только клиентом официального MAX API, не устанавливается в ОС.
- PDF в дополнительном API читается в отдельном процессе без унаследованных ключей: один парсер одновременно, до 5 МБ/10 страниц/20 000 символов, 8 секунд wall-time; Linux дополнительно ограничивает память 512 МБ и CPU 5 секундами. Это ограничение ресурсов, не полноценная ОС-песочница. В MAX принимается текст.
- `/demo` использует только встроенные вымышленные примеры. Хранятся этап репетиции и предыдущий шаг диалога; пользовательские резюме в демонстрации не собираются. Сообщения демонстрации проходят через обычную очередь только своему аккаунту.
- Не обещаем защиту от целевого DDoS, абсолютное распознавание персональных сведений или exactly-once доставку. Не реализованы мониторинг с оповещениями и многосерверная очередь.
- SQLite write-lock во время доставки ограничивает параллелизм; MAX HTTP timeout — 12 секунд. Для реального роста нужны нагрузочные измерения и другой механизм очереди.
- Ротация секретов, сроки хранения, доступ оператора, резервные копии и права на исходный код требуют отдельного подтверждения перед реальным пилотом.
- Этот перечень основан на коде и автоматических тестах, не является независимым пентестом.

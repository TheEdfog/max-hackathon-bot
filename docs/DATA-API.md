# DATA-API для технической проверки

## Статус: локально проверенный черновик, не готов к передаче на удалённую проверку

В корне проекта находятся `DATA-API.yaml` и соответствующий бэкенду `openapi.json`.
Публичного API пока нет. `https://deployment-required.invalid` — намеренно неработающая заглушка, не адрес стенда. После развёртывания заменить `api.baseUrl` на реальный HTTPS URL **нашего бэкенда**, не ссылку на MAX-бота и не адрес API MAX. Поле `teamId` необязательно по схеме: его можно добавить после подтверждения номера команды организаторами; номер не выведен из имени бота.

Основа: [репозиторий организаторов](https://gitverse.ru/stasnorman/example-data-api), commit `8504a6d9b39e6f652bce689d96e88538d7541c6b`. Копии валидатора, схемы, сведения об авторе и лицензии находятся в `tools/data_api/`. Валидатор проверяет структуру, ссылки и методы OpenAPI, **но не отправляет запросы и не проверяет доступность сервера**.

## Что проверяется

15 обязательных HTTP-проверок: здоровье БД, две роли, запрет анонимного доступа, извлечение требований, создание подтверждённой вакансии, публичное чтение, изоляция работодателей, обязательное согласие, отклик, уточнение, просмотр работодателем, ручное приглашение, подтверждение и метрики. Две операции cleanup отзывают отклик и закрывают вакансию.

Текущий API при отзыве удаляет текст резюме, ответы, вопросы и приглашение; запись отклика, аудит и закрытая вакансия остаются. Это **не полное физическое удаление** тестовых объектов. Для технической проверки выделить изолированный стенд/базу; после проверки администратор удаляет стенд или тестовые записи согласно регламенту. Не выдавать закрытие вакансии за удаление. Условия полной очистки нужно согласовать перед сдачей либо отдельно реализовать безопасное удаление тестовых объектов.

## Учётные данные передаются отдельно

Нужны три разные **синтетические** учётные записи без привязки к MAX:

| Роль в DATA-API | Роль в приложении | Назначение |
| --- | --- | --- |
| `public` | Без аккаунта | Не добавлять Authorization |
| `employer` | employer | Компания технической проверки, владелец новых вакансий |
| `candidate` | candidate | Вымышленный кандидат |
| `other_employer` | employer | Другая компания для проверки запрета доступа |

Проверяющий исполнитель должен подставлять `Authorization: Bearer <JWT соответствующего аккаунта>` по значению `role`. Сама схема DATA-API не определяет протокол загрузки секретов — согласуйте эту настройку с организаторами. JWT можно получать через `POST /api/auth/login` по email/паролю, переданным защищённым каналом. Срок JWT — 12 часов; перед проверкой нужен свежий вход. Login и контракт его тела присутствуют в `openapi.json`. Вход через MAX для автоматических HTTP-проверок не требуется; токен бота передавать проверяющему исполнителю не нужно.

Аккаунты заранее создаются на тестовом стенде; для employer требуется отдельный код доступа. Не используйте аккаунт владельца бота. У employer и candidate не должно быть MAX ID: иначе действия могут отправлять уведомления. Это проверяется в начале сценария. Имена кандидата в процессе меняются на синтетическое тестовое имя.

## Проверка структуры официальным валидатором

Из корня проекта, в окружении с Python 3.13 и установленными runtime-зависимостями:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-data-api.lock
.\.venv\Scripts\python.exe tools/data_api/validate_data_api.py DATA-API.yaml
```

Успех: код завершения `0`, сообщение о соответствии версии `1.0`. Схема уже находится рядом с валидатором. Нулевой код при URL-заглушке подтверждает **только структуру**, не готовность сдачи.

## Выполнение сценария локально

```powershell
.\.venv\Scripts\python.exe -m pytest hiring_tests/test_data_api.py -q
```

Тест читает именно `DATA-API.yaml`, подставляет значения `extract`, выполняет запросы и проверяет коды, типы, обязательные поля и JSON Schema ответов. Полная цепочка выполняется дважды с cleanup, чтобы проверить повторный запуск. Это изолированный FastAPI TestClient с временной SQLite и синтетическими аккаунтами, а не проверка сети или HTTPS. Работающий бот и его база не изменяются; сообщений в MAX тест не отправляет.

## Обновление OpenAPI

```powershell
.\.venv\Scripts\python.exe scripts/export_hiring_openapi.py
```

Экспорт создаёт схему из актуального приложения, используя отдельную базу в памяти. Тест обнаружит рассогласование `openapi.json` с бэкендом. Обновляйте вместе с изменением маршрутов и тел запросов.

## Перед сдачей

1. Развернуть отдельный доступный HTTPS API с работающей БД и актуальным `PUBLIC_URL`.
2. Заменить заглушку `api.baseUrl`, подтвердить `teamId`, если его требуют в форме подачи.
3. Создать три тестовые учётные записи без MAX-привязки, передать доступы защищённым способом и согласовать подстановку ролей.
4. Определить полную очистку тестового стенда; выполнить HTTP-сценарий на нём и повторно запустить валидатор.
5. Передать **DATA-API.yaml вместе с openapi.json**; не прикладывать `.env.hiring`, токен MAX, реальные резюме или SSH-ключи.

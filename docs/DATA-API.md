# DATA-API для технической проверки

## Статус: публичная тестовая песочница с изолированной БД

В корне проекта находятся `DATA-API.yaml` и соответствующий бэкенду `openapi.json`.
Проверочная песочница доступна на `https://176.108.244.193/review`; production API и его SQLite обслуживаются другим контейнером. Caddy снимает префикс `/review`, затем запрос направляется в отдельный API-контейнер с отдельным Docker-томом SQLite и собственным JWT-секретом. Тестовые пользователи синтетические, не связаны с MAX; токен MAX не передаётся в контейнер. Общие тестовые учётные данные находятся в README. Публичная песочница не предоставляет доступа к production. `teamId` необязателен и добавляется только после подтверждения организаторами.

Основа: [репозиторий организаторов](https://gitverse.ru/stasnorman/example-data-api), commit `8504a6d9b39e6f652bce689d96e88538d7541c6b`. Копии валидатора, схемы, сведения об авторе и лицензии находятся в `tools/data_api/`. Валидатор проверяет структуру, ссылки и методы OpenAPI, **но не отправляет запросы и не проверяет доступность сервера**.

## Что проверяется

15 обязательных HTTP-проверок: здоровье БД, две роли, запрет анонимного доступа, извлечение требований, создание подтверждённой вакансии, публичное чтение, изоляция работодателей, обязательное согласие, отклик, уточнение, просмотр работодателем, ручное приглашение, подтверждение и метрики. Две операции cleanup отзывают отклик и закрывают вакансию.

При отзыве удаляются текст резюме, ответы, вопросы и приглашение; запись отклика и аудит остаются как tombstone. Созданные сценарием вакансии закрываются, но остаются в изолированной БД. Это **не полное физическое удаление**. На reviewer-томе разрешены только синтетические данные; ответственный может целиком пересоздать именно его после проверки. Не удалять и не пересоздавать production-том.

## Роли и общие тестовые учётные данные

Нужны три разные **синтетические** учётные записи без привязки к MAX:

| Роль в DATA-API | Роль в приложении | Назначение |
| --- | --- | --- |
| `public` | Без аккаунта | Не добавлять Authorization |
| `employer` | employer | Компания технической проверки, владелец новых вакансий |
| `candidate` | candidate | Вымышленный кандидат |
| `other_employer` | employer | Другая компания для проверки запрета доступа |

Проверяющий использует `Authorization: Bearer <JWT соответствующего аккаунта>` по значению `role`. JWT получается через `POST /api/auth/login`; срок действия 12 часов. Login и контракт его тела описаны в `openapi.json`. Вход через MAX не требуется.

Песочница содержит три заранее созданных аккаунта, указанных в README. Пароли намеренно публичны; не переиспользуйте их в других системах. Пользователи не имеют MAX ID, поэтому уведомления не уходят реальным людям. Имена кандидатов в сценарии синтетические.

## Проверка структуры официальным валидатором

Из корня проекта, в окружении с Python 3.13 и установленными runtime-зависимостями:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-data-api.lock
.\.venv\Scripts\python.exe tools/data_api/validate_data_api.py DATA-API.yaml
```

Успех: код завершения `0`, сообщение о соответствии версии `1.0`. Схема уже находится рядом с валидатором. Нулевой код при URL-заглушке подтверждает **только структуру**, не готовность сдачи.

## Выполнение сценария локально

```powershell
.\.venv\Scripts\python.exe -m pytest hiring_tests/test_data_api.py -q
```

Тест читает именно `DATA-API.yaml`, подставляет значения `extract`, выполняет запросы и проверяет коды, типы, обязательные поля и JSON Schema ответов. Полная цепочка выполняется дважды с cleanup, чтобы проверить повторный запуск. Это изолированный FastAPI TestClient с временной SQLite и синтетическими аккаунтами, а не проверка сети или HTTPS. Работающий бот и его база не изменяются; сообщений в MAX тест не отправляет.

## Обновление OpenAPI

```powershell
.\.venv\Scripts\python.exe scripts/export_hiring_openapi.py
```

Экспорт создаёт схему из актуального приложения, используя отдельную базу в памяти. Тест обнаружит рассогласование `openapi.json` с бэкендом. Обновляйте вместе с изменением маршрутов и тел запросов.

## Перед сдачей

### Синтетические аккаунты и удалённый прогон

Сначала создать отдельную БД проверки и указать её в `HIRING_DATABASE_URL`. Команда требует подтверждения изолированной базы и не перезаписывает существующие доступы:

```sh
python -m hiring.verify_accounts --isolated-test-db --public-review-accounts --output data/verification-accounts.json
```

Файл с доступами игнорируется Git. Общие пароли можно создавать только в изолированной reviewer-БД; этот файл служит для восстановления/локального runner:

```sh
python -m pip install -r requirements-hiring-test.lock
python tools/data_api/validate_data_api.py DATA-API.yaml
python tools/data_api/check_data_api.py --isolated-test-server --credentials data/verification-accounts.json
```

Runner входит заново, не печатает JWT/пароли, проверяет отсутствие MAX-привязок и выполняет YAML-сценарий дважды с cleanup. Он не заменяет официальный структурный валидатор. Публичные вымышленные сценарии ручной проверки: `examples/pilot-cases.json`.

OpenAPI явно объявляет Bearer JWT для защищённых маршрутов. Название команды the_swarm не определяет `teamId`: идентификатор комиссии нужно получить отдельно.

1. Передать **DATA-API.yaml вместе с openapi.json**; адрес уже указывает на reviewer-песочницу.
2. Использовать опубликованные в README тестовые роли и выполнить HTTPS runner дважды.
3. Не прикладывать `.env.hiring`, `.env.review`, токен MAX, реальные резюме или SSH-ключи.

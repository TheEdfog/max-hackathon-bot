# РезюмИТ Найм: план подготовки к хакатону MAX

Дата исследования: 22 сентября 2026. Это план, а не отчёт о завершении перечисленных работ.
Базовая версия: `57da6a0`, ветка `feature/rezumit-hiring`, PR №1.
Дедлайн 30 сентября указан участником; точное время, часовой пояс и период доступности стенда нужно подтвердить у организаторов.
Команда: 3 человека. Загрузка каждого пока неизвестна; календарь ниже — рабочая гипотеза, не обещание срока.

## 1. Решение

Не переписывать продукт с нуля. Сохранить Python/FastAPI, базовую модель вакансий/откликов, объяснимое сопоставление, API и очередь уведомлений. Основной пользовательский интерфейс — MAX-бот, без обязательного сайта или мини-приложения.

Предлагаемое позиционирование: помощник работодателя, который собирает недостающие сведения об опыте кандидата и готовит проверяемую карточку для решения о первичном интервью. Не «ИИ, который выбирает лучших людей», не автоматические отказы и не полная ATS.

Первый сегмент — небольшая IT-команда с повторяющимся наймом junior Python-разработчиков. Это гипотеза для проверки с работодателем, не установленный факт рынка. Если доступный пилот имеет другую похожую роль, изменить профиль требований, а не весь продукт.

Основной результат: работодатель получил карточку с источниками утверждений, отправил приглашение, кандидат подтвердил интерес. Статус «готов к просмотру» не означает соответствие вакансии или подтверждённую компетентность.

## 3. Что реально проверено и что нужно переделать

Исследован код `hiring/`, тесты, CI, Docker-конфигурация, DATA-API и документация. Это предметная проверка для планирования, не полный аудит безопасности и не проверка живого MAX на всех устройствах.

### Уже полезная база

- Есть сценарии вакансии, согласия, отклика, уточнений, просмотра, приглашения, подтверждения и отзыва.
- Решение принимает человек; сопоставление показывает источники и неизвестные сведения.
- Есть сохранение сессии, журнал событий и очередь отправки.
- GitHub Actions прошёл тесты, структурный валидатор DATA-API и сборку Docker-образа. Это не доказывает запуск контейнера или работоспособность удалённого стенда.
- Повторный локальный запуск 22 сентября: `python -m pytest hiring_tests -q` — 26 passed, 2 предупреждения об устаревающих интерфейсах Starlette/httpx/anyio, 9,26 секунды. Найденные выше контрпримеры показывают, что зелёные существующие тесты ещё не покрывают все важные случаи.

### Подтверждённые пробелы

1. **Ошибки интерпретации отрицаний.** Локальный вызов `hiring.matching.evidence` на синтетических данных дал `mentioned` для «Python не изучал» и `negative` для Python в «Python использовал, Docker не использовал». Нельзя трактовать эти результаты как подтверждённые навыки. Исправлять через регрессионные примеры, не простым наращиванием одного regex без проверок.
2. **Недостаточная устойчивость входных событий.** Синтетическое событие с recipient неправильного типа вызывает AttributeError в обработчике до обращения к БД. Сейчас исключения этого типа не входят в обработку ошибок polling-цикла. Это проверка дефектного входа, а не утверждение, что MAX присылает такой формат.
3. **Чат перегружен техническими командами.** Основные действия требуют UUID; есть лимит первых 20 записей без перехода дальше. Просмотр кандидата отправляет много отдельных сообщений. Нужны компактные карточки, callback-кнопки и пагинация.
4. **Недостоверная подсказка о мини-приложении.** Бот предлагает загрузить PDF в мини-приложение, хотя доступный опубликованный mini-app не подтверждён. Убрать такое обещание; дальше либо честный текстовый ввод, либо приём текстовых PDF прямо ботом.
5. **Продакшен ещё не подготовлен.** Локальный polling не заменяет внешний сервер. В официальных MAX API docs для production предусмотрен webhook. Требуется стабильный HTTPS и проверяемый процесс развёртывания.
6. **Отзыв данных нуждается в доработке.** По коду очищается Application, но это не очищает копии текстов в Outbox и не отменяет связанные ожидающие отправки. Нужны связи сообщений с откликом, политика хранения и тест отзыва. Уже доставленное в MAX сообщение нельзя объявлять удалённым из всех мест.
7. **Очередь и ошибки недостаточно наблюдаемы.** Есть повторные попытки, но исключения скрываются; нет удобного сигнала о failed-сообщениях. В нескольких процессах нет механизма захвата одной записи очереди. Для MVP явно ограничить один sender-процесс и проверить его перезапуск; не обещать exactly-once доставку.
8. **Комплект запуска противоречив.** Корневые legacy Docker/README/env могут направить проверяющего к старому продукту. Нужен один очевидный способ запустить именно бота.
9. **DATA-API пока черновик.** Успешная схема при `deployment-required.invalid` не означает удалённую готовность; cleanup не является полным физическим удалением всех тестовых сущностей.
10. **Польза и тиражирование пока гипотезы.** Встречи с комиссией не заменяют проверки с реальным работодателем. Подтверждённого работодателя для пилота и результатов замера в материалах нет.

## 5. План работ и критерии приёмки

### P0 — допуск, качество основного сценария, данные

**A. Зафиксировать продукт и проверяемые требования.**
- Один сегмент, одна вакансия для демо, основной результат до подтверждения интереса к интервью.
- Разметить 30–50 синтетических примеров: отрицания, конфликт, неизвестный опыт, разные языки/алиасы, нерелевантный ответ, одинаковые навыки при разных именах.
- Приёмка: для каждого примера заданы ожидаемые состояния и источники; цифры «экономии» пока обозначены как гипотезы.

**B. Исправить matching и границы обработки событий.**
- Файлы: `hiring/matching.py`, `hiring/bot.py`, `hiring/polling.py`, новые регрессионные тесты в `hiring_tests/`.
- Не подменять «заявлено в резюме» на «доказано». Не строить рейтинг найма по проценту упомянутых слов. При неоднозначности — уточнение/ручная проверка.
- Приёмка: известные контрпримеры проходят; неверные типы/пустые вложения/повтор события не останавливают обработку; чужие объекты недоступны.

**C. Переделать основной диалог, сохранив backend.**
- Файлы: `hiring/bot.py`, `hiring/employer_bot.py`, MAX-клиент, тесты.
- Кнопки: вакансии, кандидаты, детали, пригласить, подтвердить, отозвать с подтверждением. Текстовый ввод остаётся для описаний и ответов, slash-команды — запасной путь.
- Добавить `message_callback`, проверку владельца действия, устаревших кнопок и повторных нажатий; корректный ответ на callback.
- Компактная карточка: требование → сведения кандидата/цитата → что уточнить. Подробнее по кнопке; пагинация списка.
- Приёмка: основной путь не требует копирования UUID; нет тупика после отмены/перезапуска; полностью пройден в мобильном и веб-MAX двумя аккаунтами.

**D. Защитить данные и сделать очередь управляемой.**
- Файлы: `hiring/services.py`, `hiring/bot.py`, `hiring/db.py`, `hiring/main.py`, конфигурация, тесты.
- Общая доменная операция отзыва для API и бота; отмена ожидающих сообщений с отозванными данными; минимизация и срок хранения уже отправленных payload в серверной очереди.
- Разделение работодателей, авторизация callback, ограничение попыток работодателя, проверка webhook secret и входных размеров.
- Метрики очереди и ошибки без содержимого резюме/токенов. Зафиксировать модель повторной доставки и порядок восстановления.
- Приёмка: нельзя получить или пригласить чужого кандидата; повтор запроса не повторяет бизнес-действие; отзыв проверен по базе и очереди, ограничения сообщений MAX честно описаны.

**E. Развернуть проверяемый стенд.**
- Сначала согласовать сервер, домен/HTTPS, бюджет и владельца. Для прежней Yandex VM ранее обнаружена смена SSH host key: подтвердить через доверенный доступ, не отключать проверку ключа.
- HTTPS reverse proxy → FastAPI/webhook → БД и один sender-процесс. Polling остаётся локальным dev-режимом, не работает одновременно с webhook.
- Один актуальный корневой compose и env.example; legacy-материалы отделить без потери исходников. Сохранить данные в volume, проверить резервную копию и восстановление.
- SQLite допустима для одного экземпляра при подтверждённых ограничениях; не мигрировать на PostgreSQL только ради презентации. Несколько экземпляров потребуют отдельного решения для БД/очереди.
- Приёмка: чистая машина запускает документированной командой; healthcheck, перезапуск, восстановление данных и уведомлений проверены; сервер доступен без ноутбука участника весь период оценки.

**F. Завершить API-комплект.**
- Файлы: `DATA-API.yaml`, `openapi.json`, `docs/DATA-API.md`, синтетический fixture, тесты/инструкция проверки.
- Реальный baseUrl; актуальные схемы и объявленная авторизация; три тестовых аккаунта без MAX-привязки, без доступа к реальным данным.
- Согласовать подстановку ролей/получение JWT и очистку стенда с исполнителем проверки. Не выдавать 12-часовой токен за постоянный доступ.
- Приёмка: официальный валидатор + полный сценарий через HTTPS с другого компьютера, два повторных запуска с понятной очисткой; набор данных воспроизводим.

### P1 — доказательство ценности и полный пакет сдачи

**G. Короткий пилот с работодателем.**
- 2–3 беседы по возможности, минимум один представитель целевого сегмента, наблюдаемое сравнение ручного процесса и бота на согласованном наборе синтетических данных.
- Метрики: активное время рекрутера на отклик, количество ручных уточнений, завершение анкеты, неверные утверждения в карточке, время до решения о приглашении.
- Цель-гипотеза: уменьшить активное время первичной обработки на 30% без потери важных сведений. Это не достигнутый результат и не обещание.
- Использовать сопоставимые кейсы и учитывать эффект повторного знакомства с резюме; фиксировать число участников и выборку. Малую выборку не выдавать за статистическое доказательство.
- Если работодателя нет — честный исследовательский прототип, экспертный отзыв комиссии и план пилота; не называть это проведённым внедрением.

**H. Масштабирование и защита.**
- Первый контекст: команда, с которой согласован пилот. Следующий: другая IT-команда с тем же профилем; затем смежная роль QA/support после адаптации словаря и вопросов.
- Сохраняются: согласие, отклик, карточка, приглашение, уведомления. Меняются: требования вакансии, проверочный набор, права и правила хранения, каналы привлечения кандидатов.
- Для каждого шага назвать необходимые данные, владельца процесса, ресурсы/расходы, критерий успеха и ограничения. Конкретные названия организаций — только после подтверждения, не выдумывать партнёров.
- Подготовить PDF, схему архитектуры, краткий сценарий демо, ограничения, происхождение кода, ответы на «почему MAX», «почему не обычная форма», «что делает человек», «как проверили пользу».
- Закрытый служебный первый слайд передавать только через подтверждённый канал организаторов. В публичном PDF/GitHub никаких рабочих токенов, паролей или реальных резюме. Необходимость каждого секрета и минимальные права согласовать; не включать инфраструктурные root-доступы по умолчанию.

### P2 — только после готового P0

- Текстовые PDF прямо в чате: заранее ограничить размер/число страниц, таймаут и расход памяти; не доверять URL вложения, защититься от произвольной загрузки адресов; сканы/OCR пока исключить, дать понятный fallback на текст.
- Дополнительная полезная возможность MAX — только если комиссия подтверждает соответствие бонусу и есть время на сквозной тест. Не добавлять её ради количества функций.
- Не входят до 30 сентября: полноценная ATS, автоматические отказы, массовый парсинг внешних резюме, оценка личности, универсальный рынок профессий, новый сайт, сложная аналитика, миграция стека ради моды.

## 7. Финальный чек-лист

- [ ] Работодатель → вакансия → кандидат → согласие → сведения → уточнения → карточка → приглашение → подтверждение, без вмешательства разработчика.
- [ ] Повторный вход, отмена, закрытая вакансия, неверное сообщение, повтор callback, недоступность MAX, рестарт и чужой работодатель проверены.
- [ ] Набор проверки matching проходит; проценты покрытия не выданы за качество кандидата.
- [ ] Сервис и HTTPS живут независимо от локального ПК; ответственный за поддержку известен.
- [ ] Чистая Docker-сборка укладывается в лимит, контейнер реально запускается и сохраняет данные после рестарта.
- [ ] DATA-API и OpenAPI соответствуют сдаваемому commit; удалённые сценарии проверены; аккаунты/fixture/очистка подготовлены.
- [ ] Нет секретов в публичных файлах/истории сдаваемого проекта; права на исходную работу и зависимости описаны.
- [ ] README, env.example, lock-файлы, схема архитектуры, ограничения и порядок проверки актуальны.
- [ ] PDF подготовлен; публичная копия очищена; приватная передаётся только организаторам.
- [ ] Измеренные результаты отделены от целей; масштабирование конкретно; роли команды объяснимы.
- [ ] Рабочие ссылки, версия стенда и commit hash совпадают; сдача подтверждена; версия заморожена по правилам этапа.

## 8. Что уточнить у комиссии и команды

1. Точное время дедлайна 30 сентября и до какой даты обеспечивать доступность стенда.
2. Допустимость использования ранее созданной основы с разрешением автора; требуемый формат подтверждения прав.
3. Канал передачи служебного PDF и тестовых доступов; какие секреты действительно нужны проверяющему.
4. Как проверяющий получает JWT по ролям DATA-API и какой объём очистки тестовых данных требуется.
5. Какая конкретная дополнительная возможность MAX соответствует платформенному бонусу.
6. Кто реальный работодатель для теста и сколько времени могут выделить три участника.
7. Доступный сервер, домен, согласованный бюджет и подтверждение SSH-ключа существующей VM.

# Что нужно от владельца для сдачи

## 1. Постоянный HTTPS-стенд

Статус 30 сентября 2026: production VM и HTTPS работают, webhook активен, локальный polling остановлен. [Production health](https://176.108.244.193/health); отдельная reviewer-песочница API опубликована в README по `/review`. Данные и JWT-секрет тестовой песочницы отделены от production.

Это облачный сервер, на котором бот и API продолжают работать без включённого домашнего компьютера. HTTPS нужен нашему HR API и webhook MAX. Сам бот открывается по прежней ссылке в MAX, отдельный сайт продукта не требуется.

От владельца нужны:

1. Выбранный российский хостинг и созданная Linux VM с возможностью запускать Docker. Покупку/активацию аккаунта и выбор бюджета выполняет владелец. Другой вариант - управляемая площадка с публичным HTTPS и постоянным диском, но её совместимость надо проверить отдельно.
2. IP сервера, SSH-имя пользователя и путь к локальному приватному ключу. Сам ключ не вставлять в Git или публичное сообщение. SSH host key сверить в доверенной консоли хостинга.
3. DNS-имя, выданное площадкой HTTPS-имя или доверенный сертификат публичного IP. В текущем развёртывании используется IP-сертификат Let's Encrypt; DNS не нужен. Порты 80/443 должны оставаться доступными. Собственный платный домен по FAQ не обязателен.
4. Подтверждённый бюджет и ответственный, который не выключит стенд до окончания проверки.

После этого техническая часть: запуск Docker и Caddy, перенос локальных секретов, согласованная база/backup, отключение локального polling, регистрация одного webhook, проверка с внешней сети, обновление DATA-API и фиксация версии. Порядок есть в [DEPLOYMENT.md](DEPLOYMENT.md). Не запускать polling и webhook одновременно.

## 2. Закрытый комплект для проверяющих

Это файлы, передаваемые через личный кабинет хакатона или другой согласованный закрытый канал, а не публичный GitHub:

- Настоящий HTTPS API и ссылка на бота MAX.
- Замороженный commit/архив исходников с SHA-256, Docker-инструкция, OpenAPI, DATA-API и синтетические данные.
- Тестовые API-аккаунты работодателя, кандидата и другой компании для проверки изоляции: логины/пароли намеренно опубликованы в README и действуют только в изолированной песочнице `/review`.
- Код входа работодателя в MAX и порядок прохождения обеих ролей. Пароли от личного MAX-аккаунта участника не передаются.
- Нужные переменные окружения/ограниченные технические ключи, если их требуют организаторы для воспроизведения. Выдавать минимум прав, отдельно от публичных слайдов, с планом отзыва после проверки. В версии 1.7 LLM нет, ключи моделей передавать не нужно.
- PDF-презентация с закрытым служебным первым слайдом. Её публичная копия остаётся без секретов.

Песочница принимает только заранее созданные роли; публичная регистрация выключена. Генератор `python -m hiring.verify_accounts --isolated-test-db --public-review-accounts` допустим только в контейнере `review-api` с отдельным Docker-томом. Он не создаёт MAX-аккаунты и не затрагивает рабочую базу. Для ручной проверки чат-бота по-прежнему нужны два независимых пользователя MAX; при одном аккаунте доступен учебный `/demo`.

Не нужно отдавать жюри владельческий доступ к облачному кабинету, SSH ко всей инфраструктуре или пароль от личной почты, если этого явно не требует отдельный согласованный сценарий проверки. Для обычного тестирования продукта достаточно минимальных тестовых ролей.

Дедлайн из предоставленного FAQ: 30 сентября, 12:00 МСК. Срок доступности после дедлайна уточняется у организаторов. Наличие HTTPS само по себе не завершает подготовку закрытых доступов и приёмку.

# Один MAX-аккаунт, несколько тестовых пользователей

Это **не** `/demo`. В песочнице работают настоящие вакансии, отклики, уточнения, приглашения и проверки владения из `hiring/`, но с отдельной SQLite-базой и виртуальными пользователями. Проверяет браузерную интеграцию одним физическим MAX-аккаунтом, не независимую доставку двум реальным людям.

## Границы

- Включается только явным CLI-флагом, только в development. Production и публичный API такой режим отвергают.
- База: `data/hiring.sandbox.db`; обычная `data/hiring.db` не используется. Если в песочнице обнаружены не-тестовые аккаунты, запуск отвергается.
- Входящие события принимаются только от перечисленных `--test-user`. Первый вход — только новой командой `/test`, чтобы старые сообщения не стали тестовыми данными.
- Роли: `e` — работодатель компании А; `c` — кандидат; `x` — посторонний работодатель компании Б. У каждой свой User, BotSession и кнопки; настоящая роль MAX-пользователя в основной базе не меняется.
- Все уведомления доставляются **тому же физическому аккаунту**, с префиксом `[ТЕСТ · роль]`. Для использования кнопки уведомления сначала выберите соответствующую роль. Чужие кнопки отклоняются.
- Регистрация работодателя в песочнице заменена заранее созданными тестовыми ролями. Настоящий вход по коду проверяется отдельно в обычном режиме.
- Использовать только вымышленные данные. MAX ID нужен для доставки; реальные имена профилей не копируются в виртуальных пользователей.

## Запуск

1. В обычном боте отправить `/whoami`, получить собственный MAX ID. Не брать ID из URL чата: это может быть ID бота.
2. Остановить обычный polling. Один токен нельзя одновременно использовать в двух poller-процессах, даже на разных базах.
3. Из корня проекта:

```sh
python -m hiring.polling --sandbox --test-user YOUR_MAX_ID
```

Токен по-прежнему читается из локальной `.env.hiring`; отдельный токен и копирование ключей не нужны. Не использовать в production. Во время такого запуска бот не обслуживает остальных пользователей.

4. В MAX отправить `/test`. Переключать роли кнопками «Тестовые роли» или `/test e`, `/test c`, `/test x`. Черновики каждой роли сохраняются, команда `/cancel` отменяет только текущий шаг активной роли.

## Реальный тестовый цикл

Результаты прогона через реальный веб-клиент: [приёмка 27.09.2026](MAX-WEB-ACCEPTANCE-2026-09-27.md).

1. Работодатель: новая вакансия → описание → проверка требований → публикация.
2. Кандидат: открыть ссылку этой вакансии или отправить `/start apply_ID` → согласие → вымышленное резюме → уточнения.
3. Другой работодатель: попытаться открыть `/view ID_ОТКЛИКА`; ожидается «Отклик не найден».
4. Исходный работодатель: карточка с цитатами → приглашение.
5. Кандидат: подтверждение. Исходный работодатель видит подтверждение и обновлённую сводку.
6. Кандидат: отзыв → подтверждение очистки. Исходный работодатель больше не открывает карточку.
7. Проверить старую кнопку другой роли: не меняет данные. Вернуться к черновику после переключения и после рестарта.

## Возврат к обычной работе

Остановить sandbox-процесс и запустить `python -m hiring.polling` без флагов (или `RUN-BOT.cmd`). Обычная база и роль сохраняются. Тестовые данные не переносятся в основной контур; файл песочницы остаётся локально, не удаляется автоматически и не публикуется в Git.

## Бесплатные модели при разработке

Для ограниченной синтетической задачи использован анонимный OVHcloud Qwen3-Coder: один успешный запрос, 144 входных + 190 выходных токенов. Черновик помог выбрать случаи восстановления состояния и маркировки уведомлений; не являлся ревью безопасности. Следующий запрос на черновик тестового кода вернул HTTP 429, без повторов/платного fallback. Код авторизации и окончательная проверка выполнены локально. Данные профиля, чата, ключи и резюме провайдеру не отправлялись.

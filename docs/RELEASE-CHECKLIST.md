# Передача проекта

## Локальная проверка

Из корня репозитория в Python 3.13:

```sh
python -m pip install -r requirements-hiring-test.lock
python -m pip check
python tools/data_api/validate_data_api.py DATA-API.yaml
python scripts/release_check.py
python -m pytest hiring_tests -q
python scripts/smoke_hiring.py --local
python scripts/release_check.py --history
```

Локальный smoke запускает временный API и SQLite с вымышленными аккаунтами, проходит создание, перезапуск и восстановление копии базы. Он не запускает MAX и не касается рабочей БД. `--history` сверяет значения из локального `.env.hiring` с отслеживаемыми файлами и Git-историей; печатает только имена совпавших файлов, не секреты. Эта проверка не распознаёт неизвестные и закодированные секреты.

GitHub Actions дополнительно собирает Docker-образы, выполняет HTTP-сценарий после перезапуска и проверяет Caddy. Дождитесь успешных проверок именно на сдаваемом commit.

## Внешние шаги команды

1. Обновить и отрепетировать презентацию, сверив её с фактической версией бота.
2. Передать комиссии закрытый комплект: постоянный HTTPS URL, зафиксированный commit, синтетические тестовые роли и отдельные доступы. Не помещать пароли и токены в публичный репозиторий.
3. Выполнить удалённый DATA-API сценарий на отдельном стенде с синтетическими ролями. Подробности и ограничения — в [DATA-API.md](DATA-API.md).
4. Если возможно, завершить ручную проверку MAX двумя независимыми аккаунтами и на мобильном клиенте.

Публичный IP, работающий HTTPS и короткая проверка MAX описаны в [облачной приёмке](MAX-CLOUD-ACCEPTANCE-2026-09-28.md). Это не заменяет независимый двухаккаунтный прогон. История и границы проверки на дату релиза — в [RELEASE-READINESS.md](RELEASE-READINESS.md).

# Интеграция работодателя: API v1

API работает в том же контейнере, что MAX webhook; наружу публикуется только HTTPS через Caddy. Работодатель подключает **свой сервер**, не браузер кандидата. Не открывайте Docker socket, SQLite или внутренний порт API в интернет.

Схема: `/openapi.json`, интерактивная справка `/docs`. Префикс машинных методов: `/api/integrations/v1`. Реализация и тесты есть; подключение к конкретной коммерческой ATS не заявляется.

Версия 1.7: удалённые методы и изменения схем описаны в [SIMPLIFIED-1.7.md](SIMPLIFIED-1.7.md).

## Получение доступа


Одна компания в MVP — один аккаунт работодателя. Ключи принадлежат этому аккаунту; ключ другой компании не читает его объекты. Командные роли внутри компании пока не реализованы. API-регистрация работодателя (`POST /api/auth/register`) создаёт отдельного владельца данных, а не подчинённого администратора.

Следующий безопасный шаг для командного режима: отдельная `Company` и membership-роли `admin`/`recruiter`; администратор выпускает одноразовое приглашение с коротким сроком действия, MAX-пользователь сначала подтверждает собственную личность через MAX и затем принимает приглашение. Все запросы к вакансиям, откликам, ключам и событиям должны проверять `company_id`, а отключение участника — немедленно отзывать его ключи и сессии. Проверять двумя компаниями, двумя рекрутерами одной компании, кандидатом и MAX-пользователем с отозванным/истёкшим приглашением. Это намеренно не подменяется общим паролем или повышением роли кандидата по одному номеру MAX.

Работодатель с обычным API-входом получает JWT через `/api/auth/login` и вызывает `POST /api/integration-keys`:

```json
{"name":"ATS read-only","scopes":["jobs:read","applications:read","events:read","metrics:read"],"expires_in_days":30}
```

Ответ 201 содержит `token` **один раз**. Хранить его в секретах HR-сервера; не в браузере, Git, URL или логах. Для дальнейших запросов: `Authorization: Bearer <token>`. JWT и машинный ключ не взаимозаменяемы. В БД сохраняется только SHA-256 хеш случайного ключа. Срок 1–90 дней, по умолчанию 30; максимум 20 действующих ключей на компанию.

`GET /api/integration-keys` показывает метаданные без секретов. `DELETE /api/integration-keys/{id}` отзывает ключ; последующие запросы с ним получают 401. Для ротации выпустите новый ключ с теми же минимальными правами, замените секрет на HR-сервере, затем отзовите старый. Уже начавшийся запрос может завершиться.

Для работодателя, зарегистрированного только в MAX, администратор стенда может выпустить ключ локально:

```sh
python -m hiring.integration_keys --owner-id INTERNAL_EMPLOYER_ID --name ATS --scope jobs:read --scope applications:read --scope events:read
python -m hiring.integration_keys --owner-id INTERNAL_EMPLOYER_ID --revoke KEY_ID
```

Это явная административная операция; первая команда печатает секрет один раз. Не запускайте её в записываемом публичном терминале/CI. Внутренний ID проверяется администратором в локальной таблице `hiring_users` по уже подтверждённому работодателю; это не номер чата MAX. Не выдавайте доступ только на основании присланного номера. Демонстрационным аккаунтам ключи запрещены, CLI также запрещает sandbox-персоны.

## Компания, администратор и рекрутеры

`POST /api/auth/register` с `role=employer` создаёт отдельную компанию; зарегистрированный пользователь получает роль `admin`. У работодателя должен быть код, выданный оператором сервиса. Затем он входит через `POST /api/auth/login` и получает короткоживущий JWT. Публичный RSA-ключ не используется: для API применяются JWT и случайные ограниченные integration keys, а MAX ID определяется по подлинному sender ID входящего события бота.

1. Администратор вызывает `POST /api/company/max-link`. API возвращает одноразовую команду `/connect connect_…`, действующую 10 минут. Администратор отправляет её боту в личный чат. Backend связывает MAX ID из webhook с уже аутентифицированной учётной записью.
2. Для коллеги администратор вызывает `POST /api/company/recruiter-invitations`. Команда `/join join_…` действует 24 часа. Администратор передаёт её лично, а сотрудник отправляет боту в личном чате. MAX ID берётся из события от MAX, не из текста команды. Создаётся отдельный участник с ролью `recruiter` и доступом к данным этой компании.
3. Вакансии, отклики, шаблоны тестов, метрики и integration keys изолируются по внутреннему `company_id`, а не по совпадению названий компаний. Каждое API-действие HR-системы проверяется в границах той же компании. Администратор управляет участниками через `GET /api/company/members` и отзывает доступ через `DELETE /api/company/members/{member_id}`. При отзыве блокируются JWT/MAX-доступ, ключи рекрутера отзываются, а его вакансии и тесты переходят администратору компании.

Инвайты одноразовые, хранятся как хеш, имеют срок действия и не повышают роль существующего пользователя. Если MAX ID уже занят другой записью, привязка отклоняется; автоматического слияния резюме и откликов нет. Для команды нужен отдельный MAX-аккаунт рекрутера. Поддержка передачи админства и восстановления конфликтных аккаунтов пока не входит в этот поток.

Публичный `/review` — отдельная база без MAX webhook и без реальных учёток. Там можно проверить вход и company-scoped HR API, но одноразовые MAX-команды связывания/приглашения проверяются на основном API и тестируются автоматическими webhook-сценариями. Не используйте пароли из публичного README для регистрации в рабочей базе.

## Права и операции

| Право | Методы после префикса v1 |
| --- | --- |
| `jobs:read` | GET `/jobs`, `/jobs/{id}` — условия, требования, активность, ссылки отклика, внешний ID |
| `jobs:write` | PUT `/jobs/by-external/{source}/{external_id}`; PATCH `/jobs/{id}` с `{"active":false}` (закрыть приём) или `{"active":true}` (открыть) |
| `applications:read` | GET `/applications`, `/applications/{id}` — статусы и прогресс без текстов кандидата |
| `applications:pii` | Вместе с `applications:read`: текст, имя, ответы, цитаты и история **в детальной карточке** |
| `invitations:write` | POST `/applications/{id}/invite` с `{"message":"…"}` |
| `applications:decision` | POST `/applications/{id}/reject` — отказать и поставить уведомление кандидату в очередь MAX |
| `events:read` | GET `/events?after=0&limit=100` — изменения вакансий и откликов |
| `metrics:read` | GET `/metrics` — активные вакансии и фактические статусы |
| `tests:read` | GET `/tests`, `/tests/{id}` - собственная библиотека и закрытые критерии проверки |
| `tests:write` | POST `/tests`, PUT `/tests/{id}` - создание, новая версия, архивирование |

По умолчанию выдаются четыре read-права без PII. Список откликов не содержит резюме даже с PII-правом. Наличие права не заменяет согласованный порядок обработки данных работодателем.

Закрыть вакансию можно через `PATCH /jobs/{id}` с правом `jobs:write` и телом `{"active":false}`. Сохранённые отклики остаются доступны; новые отклики получают `409 Приём откликов завершён`. Чтобы открыть вакансию снова, передайте `{"active":true}`.

Отправить кандидату стандартное вежливое уведомление об отказе можно запросом `POST /applications/{id}/reject` с правом `applications:decision` и без тела. Ответ `200` содержит статус `rejected` и признак доставки (`queued` или `no_max_link`). Операция идемпотентна: повторный запрос не отправляет второе сообщение. Отказ отражается в фильтре статусов и ленте событий как `application.rejected`.

## Новые методы 1.3

Все пути ниже имеют префикс `/api/integrations/v1`, если не указано иное.

### Резюме и PDF

- `GET /applications/{id}/resume.txt` - исходный текст отклика.
- `GET /applications/{id}/resume.pdf` - **оригинал** прикреплённого PDF, не заново сгенерированное резюме. Нужны `applications:read` + `applications:pii`, принадлежность вакансии компании. `404` означает, что кандидат прислал только текст; `410` - отзыв отклика. Ответ скачивается как attachment, с `no-store`, `nosniff` и SHA-256 в `X-Content-SHA256`.
- Кандидат передаёт файл через `POST /api/jobs/{job_id}/apply-pdf` (JWT кандидата, multipart: `file`, `name`, `consent=true`) или прикрепляет PDF кнопкой в MAX после согласия на обработку. Повторный отклик не заменяет уже сохранённый файл или имя. Лимиты: 5 МБ, 10 страниц, текстовый слой. OCR и DOCX не поддерживаются.
- `POST /documents/parse` (`jobs:write`, multipart `file`) извлекает текст PDF без сохранения. Парсер изолирован в процессе без ключей приложения.

### Библиотека тестов и копия для вакансии

`POST /tests`:

```json
{"title":"SQL для аналитика","questions":[{"text":"Как найти дубликаты в таблице SQL?","rubric":"GROUP BY, HAVING; обсудить NULL"}],"active":true}
```

До 3 вопросов по 10-800 символов; критерии `rubric` до 1500 символов видит только работодатель. Нет выполнения кода, автоматических оценок и автоматических отказов. `GET /tests` поддерживает `after` / `limit`; лимит библиотеки - 100 шаблонов, включая архив.

`PUT /tests/{id}` принимает тот же объект плюс `expected_version`. Для архива передайте `active=false`; версия увеличится, прежние вакансии не изменятся. Чужие шаблоны недоступны.

`PUT /jobs/{id}/assessment` (`jobs:write`): `{"template_id":"ID","expected_version":1}`. Сохраняется копия вопросов, критериев и версии. `{"template_id":null}` убирает тест. При наличии любого отклика менять тест нельзя (409). `GET /jobs/{id}/assessment` (`jobs:read`) показывает эту копию владельцу. Общий список/публичная карточка вакансии и ответы кандидату **не содержат критериев**.

В MAX: «Библиотека тестов» (`/tests`) - «Создать тест»; в черновике вакансии - «Тест для вакансии». Кандидат может пропустить задание, ответы сохраняются. Работодатель читает их через «Ответы на тест». Всего до 9 вопросов: 3 уточнения навыков + 3 об ожиданиях + 3 задания; все три группы необязательны по данным/настройкам.

Пример тела PUT вакансии:

```json
{
  "title":"Data Engineer — учебная вакансия",
  "description":"Разработка учебного Python ETL, тестирование качества данных и SQL-запросов.",
  "terms":"Удалённо; условия обсуждаются",
  "requirements":[{"id":"py","skill":"python","label":"Python"},{"id":"sql","skill":"sql","label":"SQL"}],
  "screening_questions":["screen_conditions","screen_availability"],
  "active":true
}
```

Повторный PUT с той же парой `source/external_id` у того же владельца обновляет объект, не плодит дубликаты. Смена ключа не меняет соответствие. При наличии хотя бы одного отклика можно менять только `active`: изменение условий/критериев даёт 409, создайте новую версию внешнего ID. Это сохраняет контекст уже полученных ответов. Вакансии из MAX тоже читаются через API, но без внешнего ID.

Приглашение использует ту же логику, что кнопка MAX: повтор не дублирует бизнес-переход. `delivery=queued` означает постановку в очередь, **не подтверждение доставки**; `no_max_link` — у API-кандидата нет MAX-связи. Решение о приглашении принимает работодатель, не модель.

## Надёжная синхронизация

Для обычной работы HR-системы:

- `GET /jobs/by-external/{source}/{external_id}` находит вакансию без повторной записи. Нужен `jobs:read`; совпадение ID у другой компании не даёт доступа.
- `GET /jobs?source=ats&active=true` оставляет вакансии конкретного источника.
- `created_from` (включительно) и `created_before` (исключительно) принимают ISO 8601 с часовым поясом, например `2026-09-20T00:00:00Z`. В URL знак `+` часового пояса нужно кодировать как `%2B`. Пустой/обратный интервал и даты без пояса дают 422. Фильтры сочетаются с `job_id`, `status`, `after`, `limit`; на каждой странице повторяйте все фильтры.

Постраничный список не фиксирует снимок: во время чтения статус может измениться. Для надёжного переноса изменений и удаления персональных данных используйте **нефильтрованную** ленту `/events` по алгоритму ниже. Отфильтрованная подборка кандидатов не заменяет синхронизацию отзывов.

1. Первый запуск: выгрузить все `/jobs` и `/applications`, следуя `next_cursor` до `null` (лимит 1–100). Это необходимо для объектов, созданных до установки API v1.
2. После снимка прочитать `/events` начиная с `after=0`. Повторно применяемые изменения должны быть идемпотентными. Таким образом события догоняют изменения, которые произошли во время выгрузки.
3. Для каждой записи получить актуальное состояние объекта по ID; это поток **изменившихся объектов**, а не неизменяемые исторические снимки.
4. В одной транзакции своей ATS выполнить upsert/delete и сохранить `next_cursor`. При ошибке не продвигать курсор; повтор страницы безопасен для идемпотентного приёмника.
5. Если `has_more=true`, читать следующую страницу; иначе опрашивать, например, раз в 15–30 секунд. Лимит ленты 1–200.

`seq` монотонен, но пропуски нормальны: между событиями могут быть записи других компаний. Курсор — каноническая десятичная строка, без знака/нулей слева, до 2^63−1. Нельзя вычислять его из количества записей. Временные метки сервера — UTC (SQLite может возвращать их без суффикса часового пояса).

Изменения MAX и HTTP пишутся в ту же транзакцию, что событие. При rollback событие не остаётся. После восстановления старой резервной копии оператор должен инициировать полную пересинхронизацию клиентов и сброс курсора; автоматическое распознавание смены базы пока не реализовано. Лента хранит только ID/тип/время, без резюме; автоматическая очистка ленты пока не включена. Исходящие webhooks HR-системам не реализованы: доступен pull API.

Отзыв кандидатом возвращает `{"id":"…","job_id":"…","status":"withdrawn","deleted":true}` даже ключу с PII. Получатель обязан удалить ранее сохранённые тексты, ответы и производные копии. API не может физически стереть данные на чужом сервере: это ответственность интегратора. Уже скачанные копии и резервные копии требуют отдельного регламента.

## Адаптер и ошибки

`examples/hr_sync.py` показывает получение одной страницы. Задайте `INTEGRATION_API_URL` и `INTEGRATION_KEY` в защищённом окружении, затем:

```sh
python examples/hr_sync.py --after 0
```

По умолчанию печатаются только ID/статусы. Замените функцию `summary()` на транзакционную запись в вашу ATS и сохранение курсора. Это **пример**, не готовое хранилище/checkpoint. HTTPS обязателен, HTTP допускается только для loopback; редиректы запрещены. Тесты проверяют адаптер на настоящем локальном API, повтор страницы и отказ приёмника.

Ошибки: 401 — неверный/истёкший/отозванный ключ; 403 — нет права; 404 — объект отсутствует или принадлежит другой компании; 409 — конфликт состояния; 422 — неверный формат; 429 — лимит. Общий лимит интеграции и управления ключами — 120 запросов/минуту на IP, `Retry-After: 60`. Это ограничитель одного процесса, не распределённый rate limiter. При 429/5xx используйте backoff с верхним пределом, не повторяйте неизменённые 4xx. Стенд рассчитан на один экземпляр SQLite; высокая нагрузка не подтверждена.

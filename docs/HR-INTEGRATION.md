# Интеграция работодателя: API v1

API работает в том же контейнере, что MAX webhook; наружу публикуется только HTTPS через Caddy. Работодатель подключает **свой сервер**, не браузер кандидата. Не открывайте Docker socket, SQLite или внутренний порт API в интернет.

Схема: `/openapi.json`, интерактивная справка `/docs`. Префикс машинных методов: `/api/integrations/v1`. Реализация и тесты есть; подключение к конкретной коммерческой ATS не заявляется.

## Получение доступа

Одна компания в MVP — один аккаунт работодателя. Ключи принадлежат этому аккаунту; ключ другой компании не читает его объекты. Командные роли внутри компании пока не реализованы.

Работодатель с обычным API-входом получает JWT через `/api/auth/login` и вызывает `POST /api/integration-keys`:

```json
{"name":"ATS read-only","scopes":["jobs:read","applications:read","events:read","metrics:read"],"expires_in_days":30}
```

Ответ 201 содержит `token` **один раз**. Хранить его в секретах HR-сервера; не в браузере, Git, URL или логах. Для дальнейших запросов: `Authorization: Bearer <token>`. JWT и машинный ключ не взаимозаменяемы. В БД сохраняется только SHA-256 хеш случайного ключа. Срок 1–90 дней, по умолчанию 30; максимум 20 действующих ключей на компанию.

`GET /api/integration-keys` показывает метаданные без секретов. `DELETE /api/integration-keys/{id}` отзывает ключ; последующие запросы с ним получают 401. Для ротации выпустите новый ключ с теми же минимальными правами, замените секрет на HR-сервере, затем отзовите старый. Уже начавшийся запрос может завершиться.

Для работодателя, зарегистрированного только в MAX, администратор стенда может выпустить ключ локально:

```sh
python -m hiring.integration_keys --owner-id INTERNAL_EMPLOYER_ID --name ATS --scope jobs:read --scope applications:read --scope events:read
python -m hiring.integration_keys --owner-id INTERNAL_EMPLOYER_ID --revoke KEY_ID
```

Это явная административная операция; первая команда печатает секрет один раз. Не запускать её в записываемом публичном терминале/CI. Внутренний ID проверяется администратором в локальной таблице `hiring_users` по уже подтверждённому работодателю; это не номер чата MAX. Не выдавайте доступ только на основании присланного номера. Демонстрационным аккаунтам ключи запрещены, CLI также запрещает sandbox-персоны.

## Права и операции

| Право | Методы после префикса v1 |
| --- | --- |
| `jobs:read` | GET `/jobs`, `/jobs/{id}` — условия, требования, активность, ссылки отклика, внешний ID |
| `jobs:write` | PUT `/jobs/by-external/{source}/{external_id}`; PATCH `/jobs/{id}` с `{"active":false}` |
| `applications:read` | GET `/applications`, `/applications/{id}` — статусы и прогресс без текстов кандидата |
| `applications:pii` | Вместе с `applications:read`: текст, имя, ответы, цитаты и история **в детальной карточке** |
| `invitations:write` | POST `/applications/{id}/invite` с `{"message":"…"}` |
| `events:read` | GET `/events?after=0&limit=100` — изменения вакансий и откликов |
| `metrics:read` | GET `/metrics` — активные вакансии и фактические статусы |

По умолчанию выдаются четыре read-права без PII. Список откликов не содержит резюме даже с PII-правом. Наличие права не заменяет согласованный порядок обработки данных работодателем.

Пример тела PUT вакансии:

```json
{
  "title":"Data Engineer — учебная вакансия",
  "description":"Разработка учебного Python ETL, тестирование качества данных и SQL-запросов.",
  "terms":"Удалённо; условия обсуждаются",
  "requirements":[{"id":"py","skill":"python","label":"Python"},{"id":"sql","skill":"sql","label":"SQL"}],
  "screening_questions":["screen_conditions","screen_availability"],
  "active":true
}
```

Повторный PUT с той же парой `source/external_id` у того же владельца обновляет объект, не плодит дубликаты. Смена ключа не меняет соответствие. При наличии хотя бы одного отклика можно менять только `active`: изменение условий/критериев даёт 409, создайте новую версию внешнего ID. Это сохраняет контекст уже полученных ответов. Вакансии из MAX тоже читаются через API, но без внешнего ID.

Приглашение использует ту же логику, что кнопка MAX: повтор не дублирует бизнес-переход. `delivery=queued` означает постановку в очередь, **не подтверждение доставки**; `no_max_link` — у API-кандидата нет MAX-связи. Решение о приглашении принимает работодатель, не модель.

## Надёжная синхронизация

1. Первый запуск: выгрузить все `/jobs` и `/applications`, следуя `next_cursor` до `null` (лимит 1–100). Это необходимо для объектов, созданных до установки API v1.
2. После снимка прочитать `/events` начиная с `after=0`. Повторно применяемые изменения должны быть идемпотентными. Таким образом события догоняют изменения, которые произошли во время выгрузки.
3. Для каждой записи получить актуальное состояние объекта по ID; это поток **изменившихся объектов**, а не неизменяемые исторические снимки.
4. В одной транзакции своей ATS выполнить upsert/delete и сохранить `next_cursor`. При ошибке не продвигать курсор; повтор страницы безопасен для идемпотентного приёмника.
5. Если `has_more=true`, читать следующую страницу; иначе опрашивать, например, раз в 15–30 секунд. Лимит ленты 1–200.

`seq` монотонен, но пропуски нормальны: между событиями могут быть записи других компаний. Курсор — каноническая десятичная строка, без знака/нулей слева, до 2^63−1. Нельзя вычислять его из количества записей. Временные метки сервера — UTC (SQLite может возвращать их без суффикса часового пояса).

Изменения MAX и HTTP пишутся в ту же транзакцию, что событие. При rollback событие не остаётся. После восстановления старой резервной копии оператор должен инициировать полную пересинхронизацию клиентов и сброс курсора; автоматическое распознавание смены базы пока не реализовано. Лента хранит только ID/тип/время, без резюме; автоматическая очистка ленты пока не включена. Исходящие webhooks HR-системам не реализованы: доступен pull API.

Отзыв кандидатом возвращает `{"id":"…","job_id":"…","status":"withdrawn","deleted":true}` даже ключу с PII. Получатель обязан удалить ранее сохранённые тексты, ответы и производные копии. API не может физически стереть данные на чужом сервере: это ответственность интегратора. Уже скачанные копии и резервные копии требуют отдельного регламента.

## Адаптер и ошибки

`examples/hr_sync.py` показывает получение одной страницы. Задайте `INTEGRATION_API_URL` и `INTEGRATION_KEY` в защищённом окружении, затем:

```sh
python examples/hr_sync.py --after 0
```

По умолчанию печатаются только ID/статусы. Замените функцию `summary()` на транзакционную запись в вашу ATS и сохранение курсора. Это **пример**, не готовое хранилище/checkpoint. HTTPS обязателен, HTTP допускается только для loopback; редиректы запрещены. Тесты проверяют адаптер на настоящем локальном API, повтор страницы и отказ приёмника.

Ошибки: 401 — неверный/истёкший/отозванный ключ; 403 — нет права; 404 — объект отсутствует или принадлежит другой компании; 409 — конфликт состояния; 422 — неверный формат; 429 — лимит. Общий лимит интеграции и управления ключами — 120 запросов/минуту на IP, `Retry-After: 60`. Это ограничитель одного процесса, не распределённый rate limiter. При 429/5xx используйте backoff с верхним пределом, не повторяйте неизменённые 4xx. Стенд рассчитан на один экземпляр SQLite; высокая нагрузка не подтверждена.

## Проверка с нуля

У проекта две намеренно разделённые точки входа. Сначала выберите, что именно проверяете:

| Нужно проверить | Начните здесь | Нужные доступы |
| --- | --- | --- |
| Пройти продуктовый сценарий в MAX одному человеку | `/demo` в [боте](https://max.ru/t781_hakaton_max_bot) | Аккаунт MAX |
| Проверить публичный API, роли и изоляцию компаний | `/review` и HTTPS runner ниже | Публичные синтетические учётки из `tools/data_api/reviewer-credentials.example.json` |
| Проверить реальный обмен «работодатель ↔ кандидат» через MAX | [Приёмочный сценарий](docs/ACCEPTANCE.md) | Два разных аккаунта MAX и выданный оператором код работодателя |

### 1. Быстрый показ в MAX: один аккаунт, ноль реальных данных

1. Откройте [бота](https://max.ru/t781_hakaton_max_bot), нажмите «Начать» и отправьте `/demo`.
2. Пройдите восемь шагов кнопками. Учебный режим показывает вымышленную вакансию Junior Python, уточнение по Docker, карточку кандидата и приглашение.
3. Нажмите «Выйти из демо». Вашу роль и активные вакансии бот восстановит; реальные вакансии, отклики и сообщения другим людям не создаются.

Этот сценарий объясняет продукт, но не заменяет проверку фактической доставки сообщений между двумя MAX-аккаунтами.

### 2. API комиссии: полностью удалённый синтетический прогон

Песочница `https://176.108.244.193/review` использует отдельный контейнер, SQLite-том и JWT-секрет. Она не подключена к MAX и к рабочей базе. Пароли опубликованы намеренно и годятся только для этой песочницы. Не отправляйте туда реальные резюме.

На Windows с Python 3.13 из корня репозитория выполните:

```powershell
py -3.13 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-data-api.lock -r requirements-hiring-test.lock
.\.venv\Scripts\python.exe tools/data_api/validate_data_api.py DATA-API.yaml
.\.venv\Scripts\python.exe tools/data_api/check_data_api.py --isolated-test-server --credentials tools/data_api/reviewer-credentials.example.json
```

На Linux/macOS замените Python-путь на `.venv/bin/python`. Ожидаемый результат последней команды: `PASS: two HTTPS DATA-API cycles with cleanup`. Она входит под синтетическими ролями, проверяет HTTPS-контракт из `DATA-API.yaml` дважды и очищает созданные отклики/закрывает созданные вакансии. Остаток в песочнице может включать tombstone-аудит и закрытые вакансии. Команда не меняет рабочую базу и не отправляет MAX-сообщения. При сетевой ошибке проверьте `/review/health`; не запускайте runner против корня `/` вместо `/review`.

Пользовательские OpenAPI-страницы: [рабочий API](https://176.108.244.193/docs) и [API-песочница](https://176.108.244.193/review/docs). Для ручной проверки используйте `/review/openapi.json`, тестовые учётки и только синтетические записи.

### 3. Настоящий сквозной прогон через MAX

Нужны два разных MAX-аккаунта: работодатель и кандидат. Для новой компании API-регистрации необходим одноразовый код, который выдаёт оператор сервиса; он намеренно не публикуется. Работодатель привязывает MAX командой `/connect …`, затем может пригласить рекрутера одноразовой командой `/join …`. Команды связывают учётку только с MAX ID из подлинного события бота. Публичные API-пароли из этого README нельзя использовать для входа в рабочую систему.

Полный сценарий с публикацией вакансии, согласием, PDF, уточнениями, приглашением, отказом, закрытием вакансии и ограничениями описан в [чек-листе приёмки](docs/ACCEPTANCE.md). Сейчас отмечайте выполненным только то, что реально проверили в клиентах MAX.

## Что делает продукт

Работодатель создаёт вакансию и проверяет выделенные требования до публикации. Кандидат даёт согласие, отправляет опыт текстом либо прикрепляет PDF кнопкой файла в MAX, затем отвечает максимум на три уточнения. Импорт файлов по внешним ссылкам отключён. Рекрутер видит цитаты и состояния требований: «есть упоминание», «косвенный признак», «нужно уточнить», «нет сведений». Решение о найме принимает человек; баллов и автоматического отказа нет.

Словарь сопоставляет, например, «питон» с Python. PostgreSQL даёт лишь косвенный сигнал для SQL, не считается подтверждённым опытом и ведёт к уточнению. Нормализованные навыки резюме повторно используются для того же текста. Необязательный ИИ-разбор выключен, пока компания не настроила необходимые юридические сведения и уведомление; обычный сценарий обходится без платной модели.

Для ATS предусмотрен версионированный [HR API](docs/HR-INTEGRATION.md): вакансии, отклики, PDF при отдельном разрешении, статусы, приглашения/отказы, события и отзыв ключей. Ключи ограничиваются правами и компанией.

## Разработка и проверки

Нужен Python 3.13. Для локальных тестов используйте синтетическую базу и конфигурацию из `.env.hiring.example`; никогда не переносите production `.env` в Git.

```powershell
py -3.13 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-hiring.lock -r requirements-hiring-test.lock
.\.venv\Scripts\python.exe -m pytest hiring_tests -q
.\.venv\Scripts\python.exe scripts/smoke_hiring.py --local
```

Для локального бота установите MAX-токен в личном `.env.hiring` и используйте `python -m hiring.polling --check`, затем `python -m hiring.polling`. Не запускайте polling с production-токеном одновременно с публичным webhook. `python -m hiring.doctor` проверяет конфигурацию и базу.

GitHub Actions тестирует приложение, сверяет OpenAPI, собирает Docker-образы и проверяет сохранение данных после перезапуска. Валидатор DATA-API проверяет структуру файла; отдельный HTTPS runner проверяет реально доступный reviewer API. Эти проверки дополняют, но не заменяют ручную приёмку MAX.

- `hiring/` — бот, HTTP API, хранение, интеграции и извлечение требований.
- `hiring_tests/` — тесты приложения и DATA-API.
- `tools/data_api/` — материалы формата, валидатор и HTTPS runner.
- `docs/` — [приёмка](docs/ACCEPTANCE.md), [API](docs/HR-INTEGRATION.md), [DATA-API](docs/DATA-API.md), [конфиденциальность](docs/DATA-POLICY.md), [ИИ-разбор](docs/AI-REVIEW.md), [развёртывание](docs/DEPLOYMENT.md).

Для технической проверки передаются `DATA-API.yaml` и `openapi.json`; статус структурной и удалённой проверки описан в [`docs/DATA-API.md`](docs/DATA-API.md). Презентация в `docs/presentation/` отражает более ранний снимок и требует синхронизации с текущим продуктом перед сдачей. Словарь и парсер вакансий основаны на проекте Вадима; согласия автора и организаторов получены командой. Происхождение кода и сторонние лицензии указаны в [`docs/THIRD-PARTY.md`](docs/THIRD-PARTY.md). Секреты, базы и резюме не коммитятся.

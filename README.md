# РезюмИТ Найм

MAX-бот первичного отбора для работодателя. Команда **the_swarm**: Нармаматов Алим, Огнева Анастасия, Шадрина Милана.

[Открыть бота](https://max.ru/t781_hakaton_max_bot). До переноса в облако бот зависит от включённого компьютера участника. [Веб-проверка одним аккаунтом](docs/MAX-WEB-ACCEPTANCE-2026-09-27.md) выполнена в песочнице; мобильный клиент и независимые аккаунты ещё должен проверить участник команды.

## Основной сценарий

Версия 1.5: [GigaChat через Cloud.ru](docs/GIGACHAT.md) готовит черновики тестов по выбранным навыкам через HR API. Только по явному запросу, без данных кандидатов, с лимитами и ручной проверкой. Ключ используется только runtime, не для разработки. После изучения FAQ и согласования с командой импорты Google Drive и Mail.ru отключены до разрешения организаторов. Остаются Яндекс Диск, GitHub, текст и PDF через API. [Проверка FAQ и риски допуска](docs/FAQ-AUDIT-2026-09-28.md).

Перед сдачей: [проверки и оставшиеся внешние шаги](docs/RELEASE-CHECKLIST.md), [приоритеты для защиты](docs/WINNING-PRIORITIES.md).

Версия 1.4 добавила [объяснимую оценку по адаптации модели Вадима](docs/VADIM-REVIEW.md), общий словарь IT/аналитики/управления/продаж, отдельную кнопку GitHub-обзора (профиль + README, без LLM). Актуальные источники и история проверок: [PUBLIC-SOURCES.md](docs/PUBLIC-SOURCES.md).

Работодатель входит по коду, создаёт вакансию, проверяет требования и отправляет кандидатам ссылку. Кандидат даёт согласие, отправляет текст опыта и отвечает максимум на три уточнения навыков. По выбору работодателя добавляются три вопроса об интересе, условиях и сроке выхода. Любой вопрос можно пропустить, диалог — поставить на паузу и продолжить. Работодатель читает карточку с цитатами и ожидания кандидата, приглашает на интервью. Кандидат подтверждает интерес.

В версии 1.3: библиотека тестов работодателя (до 3 заданий на вакансию, закрытые критерии, сохранение копии); [импорт публичных PDF и GitHub](docs/PUBLIC-SOURCES.md) с подтверждением кандидата; синонимы навыков и отдельные косвенные признаки (например PostgreSQL для SQL). В [HR API](docs/HR-INTEGRATION.md) доступны оригинал PDF, текст резюме, черновик вакансии из навыков, внутренние этапы/заметки/метки, библиотека тестов и защита от перезаписи устаревшей версии. Автоимпорт Mail.ru пока не реализован; Google/Yandex требуют живой проверки на собственных синтетических PDF-ссылках.

Все основные действия доступны кнопками в личном чате. Сайт и мини-приложение не нужны. Слэш-команды остаются запасным интерфейсом. Для двух ролей нужны два разных аккаунта MAX.

**Есть только один аккаунт?** Откройте `/demo` или «Учебный сценарий»: восемь шагов на вымышленных данных показывают обе роли, реальное сопоставление, уточнение, карточку и подтверждение. Демонстрация не создаёт вакансии/отклики, не меняет вашу роль и не отправляет сообщения другим людям. Это репетиция, а не замена двухаккаунтной приёмки.

Для разработчика есть [изолированная песочница с виртуальными ролями](docs/SANDBOX.md): настоящая бизнес-логика и отдельная тестовая БД, разрешённый MAX-аккаунт, без изменения основной роли пользователя. В production запрещена.

Уточнения показывают прогресс и позволяют явно сообщить об отсутствии опыта или пропустить вопрос. Пропуск не считается отсутствием квалификации. Работодателю доступна «Сводка откликов» (`/metrics`), изолированная от других компаний.

Анализ кандидата локальный: словарь и правила. Бот не отправляет резюме во внешнюю LLM, не подтверждает квалификацию и не принимает решение о найме. Процент упоминаний в API не является рейтингом. Сложные формулировки должен проверять человек. GigaChat используется отдельно, только для черновиков вопросов по фиксированному словарю навыков.

## Быстрый локальный запуск

Нужны Python 3.13, доступ к MAX API и выданный токен. Скопируйте `.env.example` в `.env.hiring`, не перезаписывая уже настроенный файл. Заполните MAX_BOT_TOKEN, HIRING_SECRET и HIRING_EMPLOYER_CODE. Токен не передавайте в терминале как аргумент и не коммитьте.

```sh
python -m venv .venv
# Активируйте окружение: Windows .venv\Scripts\activate, Linux source .venv/bin/activate
python -m pip install -r requirements-hiring.lock
python -m hiring.polling --check
python -m hiring.polling
```

`--check` проверяет имя бота и наличие webhook, не читает сообщения. Polling работает только в development. Не запускайте два polling-процесса и не используйте его одновременно с webhook.

`python -m hiring.doctor --max` проверяет конфигурацию, целостность существующей SQLite, очередь и доступ к MAX без чтения сообщений. Не выводит ключи, резюме или пользователей. OS-lock запрещает второй polling на той же базе; он не защищает от запуска этого же токена на другом компьютере/другой базе.

### Docker, одна команда

После заполнения `.env.hiring`:

```sh
docker compose up --build -d
```

Запускает FastAPI, очередь отправки и SQLite на `http://127.0.0.1:8000`. Это backend для проверки API и будущего webhook, а не публичный адрес бота. Без webhook входящие сообщения в этом режиме не поступают. Локальный чат-тест без публичного адреса: `docker compose -f compose.hiring.yml up --build -d` **вместо** основного compose.

```sh
docker compose ps
docker compose logs --tail=50 api
docker compose restart api
docker compose down
```

`down` сохраняет volume с данными. Не используйте `down -v` на стенде с нужными данными. Для проверки здоровья: `GET /health`; OpenAPI: `GET /openapi.json`. Корневой Dockerfile запускает один процесс приложения с одним sender-потоком, непривилегированным пользователем. Исторические Docker-файлы вынесены в `legacy/`.

## Будущий сервер

Инструкция: [docs/DEPLOYMENT.md](docs/DEPLOYMENT.md). Яндекс Cloud в этой версии не настроен. После получения домена и сервера запустить Caddy + API через `compose.production.yml`, проверить HTTPS и только затем явно зарегистрировать webhook. Порты: публичные 80/443, API 8000 на loopback. БД наружу не публикуется.

Подготовлен [обзор российских серверов с пробным доступом](docs/HOSTING-OPTIONS-2026-09-27.md): условия, ограничения и риск автоматического списания. Docker-конфигурация не привязана к Яндексу.

## Интеграция с HR / ATS

Версионированный [HTTPS API для HR-систем](docs/HR-INTEGRATION.md): идемпотентная загрузка вакансий по внешнему ID, список вакансий и откликов, приглашения, сводка и лента изменений. Отдельные от пользовательского входа ключи имеют права, срок действия и отзыв; тексты резюме доступны только с дополнительным правом. [Пример адаптера](examples/hr_sync.py) читает изменения и передаёт их вашей системе. Это не готовый коннектор к конкретной коммерческой ATS и не доступ к Docker daemon.

## Архитектура

| Компонент | Ответственность |
| --- | --- |
| `hiring/bot.py`, `employer_bot.py` | Диалог и бизнес-действия в MAX |
| `hiring/chat_ui.py` | Кнопки, привязанные к пользователю и состоянию |
| `hiring/services.py` | Отклик, уточнения, приглашение, подтверждение, отзыв |
| `hiring/matching.py` | Объяснимые упоминания, отрицания, неизвестные сведения |
| `hiring/db.py` | SQLite, совместимые добавочные миграции |
| `hiring/outbox.py` | Отправка, повторы, отмена, очистка отправленного payload |
| `hiring/main.py` | API и webhook с секретом |
| `hiring/integrations.py`, `integration_events.py` | Ключи HR-систем, синхронизация и транзакционная лента изменений |
| `hiring/maintenance.py` | Проверяемая резервная копия SQLite |

SQLite сериализует операции отправки/отзыва/обработки событий. Во время внешней отправки write-lock удерживается до 12 секунд: это компромисс одного экземпляра MVP, а не высоконагруженная архитектура. После сетевой неопределённости возможно повторное уведомление; exactly-once доставка не обещается. Для масштабирования потребуются отдельная очередь и пересмотр блокировок.

## Проверки

```sh
python -m pip install -r requirements-hiring-test.lock
python -m pip check
python -m pytest hiring_tests -q
python tools/data_api/validate_data_api.py DATA-API.yaml
```

Тесты используют синтетические данные и не отправляют сообщения MAX. Покрыты обе роли, кнопки, устаревшие/чужие действия, пагинация, повторные события, отзыв, конкурентные отправки, отрицания, резервная копия, миграция, API и DATA-API. CI дополнительно собирает контейнер и проверяет HTTP-цикл до и после рестарта. Новый CI должен пройти на сдаваемом commit; старый зелёный запуск не подтверждает новые изменения.

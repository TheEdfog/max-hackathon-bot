# РезюмИТ Найм

MAX-бот первичного отбора для работодателя. Команда **the_swarm**: Нармаматов Алим, Огнева Анастасия, Шадрина Милана.

[Открыть бота](https://max.ru/t781_hakaton_max_bot). До переноса в облако бот зависит от включённого компьютера участника. Полный ручной прогон в мобильном и веб-MAX ещё должен выполнить участник команды.

## Основной сценарий

Работодатель входит по коду, создаёт вакансию, проверяет требования и отправляет кандидатам ссылку. Кандидат даёт согласие, отправляет текст опыта и отвечает максимум на три уточнения. Работодатель читает карточку с цитатами, приглашает на интервью. Кандидат подтверждает интерес.

Все основные действия доступны кнопками в личном чате. Сайт и мини-приложение не нужны. Слэш-команды остаются запасным интерфейсом. Для двух ролей нужны два разных аккаунта MAX.

Анализ локальный: словарь и правила. Бот не отправляет резюме во внешнюю LLM, не подтверждает квалификацию и не принимает решение о найме. Процент упоминаний в API не является рейтингом. Сложные формулировки должен проверять человек.

## Быстрый локальный запуск

Нужны Python 3.13, доступ к MAX API и выданный токен. Скопируйте `.env.example` в `.env.hiring`, не перезаписывая уже настроенный файл. Заполните MAX_BOT_TOKEN, HIRING_SECRET и HIRING_EMPLOYER_CODE. Токен не передавайте в терминале как аргумент и не коммитьте.

```sh
python -m venv .venv
# Активируйте окружение: Windows .venv\Scripts\activate, Linux source .venv/bin/activate
python -m pip install -r requirements-hiring.lock
python -m hiring.polling --check
python -m hiring.polling
```

`--check` проверяет имя бота и наличие webhook, не читает сообщения. Polling работает только в development. Не запускайте два polling-процесса и не используйте его одновременно с webhook.

### Docker, одна команда

После заполнения `.env.hiring`:

```sh
docker compose up --build -d
```

Запускает FastAPI, очередь отправки и SQLite на `http://127.0.0.1:8000`. Это backend для проверки API и будущего webhook, а не публичный адрес бота. Без webhook входящие сообщения в этом режиме не поступают. Локальный чат-тест без публичного адреса: `docker compose -f compose.hiring.yml up --build -d` **вместо** основного compose.

```sh
docker compose ps
docker compose logs --tail=50 api
docker compose restart api
docker compose down
```

`down` сохраняет volume с данными. Не используйте `down -v` на стенде с нужными данными. Для проверки здоровья: `GET /health`; OpenAPI: `GET /openapi.json`. Корневой Dockerfile запускает один процесс приложения с одним sender-потоком, непривилегированным пользователем. Исторические Docker-файлы вынесены в `legacy/`.

## Архитектура

| Компонент | Ответственность |
| --- | --- |
| `hiring/bot.py`, `employer_bot.py` | Диалог и бизнес-действия в MAX |
| `hiring/chat_ui.py` | Кнопки, привязанные к пользователю и состоянию |
| `hiring/services.py` | Отклик, уточнения, приглашение, подтверждение, отзыв |
| `hiring/matching.py` | Объяснимые упоминания, отрицания, неизвестные сведения |
| `hiring/db.py` | SQLite, additive-миграция v1 → v2 |
| `hiring/outbox.py` | Отправка, повторы, отмена, очистка отправленного payload |
| `hiring/main.py` | API и webhook с секретом |
| `hiring/maintenance.py` | Проверяемая резервная копия SQLite |

SQLite сериализует операции отправки/отзыва/обработки событий. Во время внешней отправки write-lock удерживается до 12 секунд: это компромисс одного экземпляра MVP, а не высоконагруженная архитектура. После сетевой неопределённости возможно повторное уведомление; exactly-once доставка не обещается. Для масштабирования потребуются отдельная очередь и пересмотр блокировок.

## Проверки

```sh
python -m pip install -r requirements-hiring-test.lock
python -m pip check
python -m pytest hiring_tests -q
python tools/data_api/validate_data_api.py DATA-API.yaml
```

Тесты используют синтетические данные и не отправляют сообщения MAX. Покрыты обе роли, кнопки, устаревшие/чужие действия, пагинация, повторные события, отзыв, конкурентные отправки, отрицания, резервная копия, миграция, API и DATA-API. CI дополнительно собирает контейнер и проверяет HTTP-цикл до и после рестарта. Новый CI должен пройти на сдаваемом commit; старый зелёный запуск не подтверждает новые изменения.
